# PG-CRUD — REST-сервис управления пользователями

Учебный backend-проект: REST API на Node.js/Express с PostgreSQL, регистрацией, входом по JWT
и полным набором CRUD-операций. Без ORM — запросы к PostgreSQL напрямую через `pg`
с параметризацией.

## Стек

- **Node.js + Express** — HTTP-сервер и маршрутизация
- **PostgreSQL + `pg` (node-postgres)** — пул соединений, параметризованные запросы
- **bcryptjs** — хеширование паролей
- **jsonwebtoken** — выдача и проверка JWT
- **dotenv** — конфигурация через переменные окружения

## Возможности

- Полный CRUD: создание, чтение (список и по id), полное обновление (PUT), частичное (PATCH), удаление
- Поиск по пользователям через `ILIKE` (регистронезависимо, по имени, фамилии и email)
- Регистрация: валидация полей, проверка занятости email (409), хеширование пароля bcrypt
- Вход по email и паролю с выдачей JWT (срок жизни — 7 дней)
- **Защита CRUD-эндпоинтов JWT**: без токена — 401, с истёкшим или неверным токеном — 401
- Единый формат ошибок и корректные HTTP-коды
- `password_hash` никогда не попадает в ответы API (выборка только по белым полям)

## Установка и запуск

1. Установить зависимости:
   ```bash
   npm install
   ```

2. Создать `.env` в корне проекта (пример — в `.env.example`):
   ```env
   PORT=3000
   DB_USER=postgres
   DB_PASSWORD=postgres
   DB_HOST=localhost
   DB_PORT=5432
   DB_NAME=postgres
   JWT_SECRET=замени_на_секретную_строку
   ```

   Секрет можно сгенерировать так:
   ```bash
   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
   ```

3. Создать таблицу:
   ```bash
   psql -U postgres -d postgres -f database/schema.sql
   ```

4. Запустить:
   ```bash
   node index.js
   ```
   Сервер поднимется на `http://localhost:3000`. Открой адрес в браузере — откроется страница
   входа (`public/login.html`), после входа — таблица пользователей с поиском и редактированием.

## Эндпоинты

| Метод | Путь | Токен | Описание |
|---|---|---|---|
| GET | `/` | — | Проверка, что сервер жив |
| POST | `/register` | — | Регистрация: `first_name`, `last_name`, `email`, `password` |
| POST | `/login` | — | Вход: `email`, `password` → `{ "token": "..." }` |
| GET | `/users?search=иван` | 🔒 | Список пользователей, поиск по имени/фамилии/email |
| GET | `/users/:id` | 🔒 | Пользователь по id (404, если нет) |
| POST | `/users` | 🔒 | Создать пользователя (пароль необязателен) |
| PUT | `/users/:id` | 🔒 | Полностью обновить пользователя |
| PATCH | `/users/:id` | 🔒 | Частично обновить (только `first_name`, `last_name`, `email`) |
| DELETE | `/users/:id` | 🔒 | Удалить пользователя |

Токен передаётся заголовком: `Authorization: Bearer <token>`.

## Примеры запросов

```bash
# Регистрация
curl -X POST http://localhost:3000/register \
  -H "Content-Type: application/json" \
  -d '{"first_name":"Иван","last_name":"Петров","email":"ivan@example.com","password":"secret1234"}'

# Вход — получаем токен
curl -X POST http://localhost:3000/login \
  -H "Content-Type: application/json" \
  -d '{"email":"ivan@example.com","password":"secret1234"}'

# Список без токена — 401
curl -i http://localhost:3000/users

# Список с токеном — 200
curl "http://localhost:3000/users?search=иван" \
  -H "Authorization: Bearer ВСТАВЬ_ТОКЕН"

# Частичное обновление
curl -X PATCH http://localhost:3000/users/1 \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ВСТАВЬ_ТОКЕН" \
  -d '{"first_name":"Иоанн"}'
```

## Решения, которые стоит отметить

- **Параметризованные запросы (`$1, $2`)** во всех обращениях к БД — SQL-инъекция невозможна.
- **PATCH собирает `SET` динамически**, но только из белого списка полей (`first_name`, `last_name`,
  `email`) — нельзя обновить произвольную колонку из тела запроса.
- **Пул соединений (`pg.Pool`)** вместо одиночного клиента — корректная работа под нагрузкой,
  плюс обработчик `pool.on('error')`.
- **`RETURNING` с явным списком колонок** — из API не утекает `password_hash`.
- **Уникальный индекс на `email`** в БД + обработка `23505` → 409: защита от гонки, когда два
  запроса одновременно регистрируют один email.
- **Одинаковый ответ на неверный email и неверный пароль** — нельзя перебором выяснить,
  какие адреса зарегистрированы.
- **Токен хранится в `localStorage`** и подставляется единой обёрткой `apiFetch()`; на 401
  фронтенд сам разлогинивает и уводит на страницу входа.

## Историческая справка

До рефакторинга в базе было две таблицы: `users` (с `password_hash`, использовалась
регистрацией и входом) и `users1` (без паролей, использовалась CRUD-эндпоинтами).
Они объединены в одну таблицу `users`; данные из `users1` перенесены, а их дамп сохранён
в `database/legacy-users1-backup.sql`. Перенесённые пользователи не имеют пароля,
поэтому не могут войти через `/login` — это ожидаемо.
